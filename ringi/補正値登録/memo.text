上位のレイヤーを支える技術的な機能を提供する。
DB への永続化や外部アプリへの接続を担う。
インフラストラクチャ層は製品に依存した実装となるため製品変更の影響が大きい。
この影響が上位層に漏れ出ないような設計が必要。
例えば DB が oracle から postgresql に変わる場合でも、ドメイン層やアプリケーション層には変更が一切入らないようにする必要がある。
そのため、インフラストラクチャ層と上位層とのやり取りはインターフェースや POJO クラスを介して行うことになる。
機能説明
RepositoryImpl
RepositoryImplクラスはドメイン層のRepositoryインターフェースの実装クラス。
RepositoryImplクラスにはRepositoryインターフェースによってサービスクラスから隠蔽された外部連携の具体的なロジックを実装する。
ドメイン層から連携された DTO を外部連携仕様に合わせてフォーマット変換したり、外部連携先から取得したデータをドメインロジックが使いやすいように加工したりする。
（ドメイン層に外部システムや製品を意識させない。）
RepositoryImpl(DB)
DB アクセスを担うリポジトリ実装クラス。
本システムでは DB アクセス用ライブラリとして Mybatis を利用するので、
このリポジトリ実装クラスで Mybatis の機能を利用しつつ DB アクセスを実現していく。

RepositoryImpl(API)
API 連携を担うリポジトリ実装クラス。
RestClient を利用して他システムや他アプリケーションに API を送信する。
また他システムからのエラーが返却されるような場合はエラーハンドリングも行うこともある。
Mapper
Mapper は Mybatis 固有の Java インターフェース。
Mybatis では Mapper インターフェースを介して SQL を実行する。
Mapper インターフェースに定義した 1 つ 1 つのメソッドがそれぞれ SQL に対応する。

<<interface>> Table Mapper
Mybatis で単一テーブルへのアクセスを定義する為のインターフェース。
Table Mapperインターフェースは単一テーブルに対する CRUD を表現するメソッドが定義されており、Mybatis Generator という資源自動生成ツールによって生成される。

Table Mapperインターフェースの実装クラスは、Mybatis-CDI ライブラリによってアプリケーションの起動時に自動生成されるため、開発者が作成する必要がない。

s Table Data Gateway パターン
Table Data Gateway パターンとは、1 つのテーブルに対して DAO と DTO を一つずつ作成し、対象テーブルに対するアクセスを抽象化するデザインパターンである。

DAO は対象テーブルの CRUD 操作に対応した振る舞い（メソッド）を持つ。DTO は対象テーブルの 1 レコードに対応している。

Mybatis は Table Data Gateway パターンを効率的に実現する為のライブラリである。

本システムにおいては DAO がこのTable Mapperインターフェース、DTO が後述のTable Entityにあたる。

また、トランザクションスクリプトパターンには Table Data Gateway パターンをあわせて利用することが多い。
<<interface>> Query Mapper
DB のデータを取得する際に、単一テーブルの単位でしか取得できない場合、複雑なデータを取得したい場合に対応しきれない。
具体的にいうと、複数テーブルを結合（加工）してデータ取得したい場合である。
Query Mapper は結合 SQL に対応するデータを取得するためのものである。
（厳密には結合 SQL のみではないが、大部分が結合 SQL になるのでその前提で記載している。）
対応する実装クラスは、Mybatis-CDI により動的に作成されるので、個別に開発する必要がない。
Query Mapper(SQL マップファイル)
Mybatis でデータベースへのアクセスを定義する為の XML ファイル。
Query Mapper(xml)はドメイン層のQuery Mapper インターフェースに対応している。
Query Mapper(xml)には結合 SQL が記述されている。

表示における関心事を取り扱う層。

この層では、
クライアントからのリクエスト受付
入力データの妥当性チェック（入力項目相関チェックを含む）
リクエスト内容に対応するドメイン層の呼び出し
Web アプリケーションで扱う HTTP リクエスト や クエリパラメータ といった「表示に関する技術」はこの層で吸収する。
プレゼンテーション層より下位の層は、Web 画面から呼び出されたのかバッチから呼び出されたのかなどは意識しない。
また、クライアントにどのようなフォーマットでデータを返却するかも意識させてはいけない。
これらは全てプレゼンテーション層の責務となる。

この層で行う実装は、できるだけ薄く保たれるべきであり、ビジネスルールを含んではいけない。
機能説明
<<interface>> Api
Apiインターフェースは Web API のエンドポイントを表す。
実際のふるまいは、このインターフェースを実装したApiImplクラスに定義する。
Apiインターフェースは OpenAPI Generator から自動生成する。
注意
OpenAPI Generator で自動生成すると JAX-RS アノテーション（@Pathや@Producesなど）はApiインターフェースに付与される。

そのため、これを実装するApiImplクラスでは JAX-RS アノテーションを付与してはいけない。

もしApiImplクラスの JAX-RS アノテーションをつけると、Apiインターフェースに付与されていたアノテーションは無効になるので注意すること。
注記
JAX-RS では、一般的に API エンドポイントクラスのことをXxxxResource.javaという名前付けになることが多い。

これは API システムが RESTful 設計のもとリソース指向アーキテクチャを採用していることが前提のネーミングである。

本システムにおいては、RESTful な API ではなく、アクションベースの RPC 方式を採用している為、Resourceと命名するのは不適切である。

よって、本システムにおける API エンドポイントクラスはxxxxApi.javaという命名規則を採用している。
ApiImpl
Web API のエンドポイントを表す実装クラス。
Apiインターフェースを実装する。
以下の役割を担う。

HTTP リクエストを受付け、入力チェックを行う。
入力単体チェック： Modelクラスの Bean Validation で実施
入力相関チェック：　ApiImpl クラスが実施。
チェック済みの入力データを ServiceDto クラスに詰め込み、Service クラスに処理を委譲する。
Service クラスから返却された ServiceDto をレスポンスフォーマットに変換してクライアントに返却する。
注意
プレゼンテーション層は DB アクセスをしてはいけない。

そのためApiImplで実施するのは、入力値だけでチェックできるものに限る。

DB 上のデータとの整合性チェックはドメイン層で実施する。
Model
クライアントシステムから連携されたリクエストボディ、クライアントに返却するレスポンスデータを表現する POJO クラス。
このクラスには、Bean Validation のアノテーションの指定や、JSON と Java オブジェクトのマッピング編集仕様を定義する。
フィールドとそれに対する getter/setter を持つだけで振る舞いは持たない。
OpenAPI Generator から自動生成する。

ドメイン層がアプリケーション層に依存しないようにするために、以下の変換処理をプレゼンテーション層で行う。
ModelクラスからServiceDtoクラスへの変換処理（リクエスト）
ServiceDtoクラスからModelクラスへの変換処理（レスポンス）
これらの処理を愚直に実装すると、コードが長くなり見通しが悪くなるため、Bean マッピング機能を推奨する。
 
ドメイン層はアプリケーションのコアとなる層であり、ドメインに関する具体的な業務処理（ビジネスロジック）を担う。
実装するのに業務知識が必要な処理はドメイン層に属することになる。
ドメイン層の業務処理は UI や DB に変更があったとしても不変なものでなければならない。
そのため他のどの層にも依存しない設計とする必要がある。
ドメイン層の設計パターン
ドメイン層の設計パターンは大きく「トランザクションスクリプトパターン」と「ドメインモデルパターン」に大別される。
本システムにおける設計思想を以下に説明する。
トランザクションスクリプトパターン
トランザクションスクリプトパターンは、状態（業務データ）を保持するクラスと振る舞い（メソッド）を持つクラスを別々のクラスとして実装する。
前者の状態を持つクラスはフィールドに対する getter/setter のみが定義された POJO クラスとして実装される。
後者の振る舞いを持つクラスは、いわゆるサービスクラスであり、POJO クラスからデータを取得し計算処理やデータ加工処理を行う。
サービスクラスは状態を持たないステートレスなクラスとして実装される。
トランザクションスクリプトパターンはいわば、「手続き型プログラミング」を踏襲した設計パターンである。

トランザクションスクリプトパターンには、以下の特徴がある。
メリット
処理の流れがシンプルなので可読性が高い。
設計・実装難易度が低くキャッチアップが容易。
デメリット
ビジネスロジックがサービスクラスに集中するので肥大化を招く。
複数のサービスクラスが似たロジックを保持する傾向がある。
本システムにおけるトランザクションスクリプトパターンの利用方針
本システムでは、ドメイン層の設計思想として「トランザクションスクリプトパターン」を前提とする。

本システムは、旧システムからの更改を前提としており、
既存ロジックを最大限再利用できること。
既存ロジックをドメインモデルパターン（※）に置き換えた場合と比較しコストや品質面で優位であること。
を踏まえ、「トランザクションスクリプトパターン」を採用している。

ドメインモデルパターン
ドメインモデルパターンは、本来的なオブジェクト指向設計の原則に従い、1 つのクラスの中に状態と振る舞いを実装する。
このクラスはドメインオブジェクトと呼ばれる。

ドメインモデルパターンはトランザクションスクリプトパターンと比較した場合、以下の特徴がある。
メリット
ドメインオブジェクトは自身に関するルールや振る舞い（＝ビジネスロジック）を自分自身に持っているので、クラスの凝集度が高くなる。
同じようなビジネスロジックが複数クラスに実装されることがないので変更に強い。
サービスクラスが肥大化しにくい。
デメリット
設計難易度が高い。
ドメインモデリングが正しくできてないと複雑なロジックになり、逆にメンテナンス性が低下する。
ドメインモデルパターンは設計の難易度が高いものの業務領域を正しく設計に落とし込めれれば、
改修影響度や保守性において非常に効果的なアプローチになる。
本システムにおけるドメインモデルパターンの利用方針
上述の通り本システムでは「トランザクションスクリプトパターン」を採用するが、
ドメインモデルパターンの適用が可能かつ、効果が高い個別機能についてはドメインモデルパターンを利用する方針とする。
ドメインモデルパターンの中でも、いくつかのデザインパターンが存在するため、どのパターンを取り入れるかは個別業務機能内で検討する必要がある。

備考
以降の説明には、Eric Evans の”Domain-Driven Design (2004, Addison-Wesley)”で説明されている用語が登場する。

ただし、用語は使用しているが”Domain-Driven Design”の考えに則っているわけではないことに注意されたい。
Service
サービスクラス。
サービスクラスは以下の 2 つの役割を担う。

ビジネスロジックを提供する トランザクションスクリプトパターンにおいてはサービスクラス内にビジネスロジック（業務データの参照、更新、整合性チェックおよびビジネスルールに関わる各種処理）を実装する。

プレゼンテーション層とのデータの受け渡しは ServiceDto クラスを介して行われる。
トランザクション境界を宣言する トランザクション境界は原則 Service クラスに設ける。

データの一貫性を保障する必要がある処理（主にデータの更新処理）を行う業務ロジックの場合、トランザクション境界を宣言する。

データの参照処理の場合でも業務要件によっては、トランザクション管理が必要になる場合もあるので、その場合も、トランザクション境界を宣言する。
サービスクラスの作成単位
サービスクラスはイベント毎に作成する方針とする。
イベント毎に作成することで正しいトランザクション境界を設定できる。
イベント単位でサービスクラスを作成するとイベント内での業務ロジックの共通化は行うことができるが、イベントを跨いだ業務ロジックの共通化は行われない可能性が高くなる。
イベントを跨いで業務ロジックの共通化を行う必要がある場合は、共通化するスコープを適切に設計する工夫が必要になる。
1 サービスクラス内に複数のイベントを実装することは、保守性と可読性の観点から推奨しない。
ServiceDto
プレゼンテーション層とドメイン層間のデータの受け渡しを行うための DTO。
純粋な POJO クラスであり、ドメインロジックは持たせない。
ServiceDto クラスに設定されるデータは、プレゼンテーション層で妥当性チェックを実施済なので、 Service クラスはServiceDto のデータ妥当性をチェックする必要はない。
ServiceDto クラスは Service クラスに対しての Input と Output それぞれ必要なので単純計算で Service クラス x 2 の資源数となる。
Repository
リポジトリはインフラ層へのアクセスを抽象化するためのクラスである。
リポジトリパターンを採用することで DB アクセスや外部連携の具体的な処理は、サービスクラスからは見えなくなり
サービスクラスは永続化ストレージが何であるか（例えば MySQL や Redis など）、外部連携方式が何であるか（REST や SOA）を意識することなく Entity の取得や保存を行うことができる。

ドメイン層には Repository インターフェースのみを定義する。
実装クラスはインフラストラクチャ層に実装する。
これは、依存性逆転の原則を実現するためのもので、ドメイン層がインフラストラクチャ層に依存しないようにしている。
ドメイン層にインターフェース、インフラストラクチャ層にその実装クラスを配置することで、もし外部連携の仕様が変更になった場合（例えば、SOAP 通信から HTTP 通信になるなど）に、
インフラ層のみを改修すればよく、ドメイン層に全く改修が入らないようにできる。（つまり、ドメイン層がインフラストラクチャ層に依存していない。）
注記
本来リポジトリパターンは外部連携処理のみでなく、DB アクセスも含めてデータの入出力に広く使える概念ではあるが、本アーキテクチャにおいては外部連携のみに対してのみリポジトリパターンを適用している。

また、本システムにおける Repository は、DDD(Domain-Driven Design)における”集約”の単位で永続化を行うリポジトリとは別の文脈であるので注意すること。

<<interface>> Repository(DB)
DB アクセス用のリポジトリクラス。
実装クラスはインフラストラクチャ層に配置する。
<<interface>> Repository(API)
API 連携用のリポジトリクラス。
実装クラスはインフラストラクチャ層に配置する。
Entity
ビジネスロジックで利用する POJO クラスの総称。
Entity 自体にはビジネスロジックは実装しない。
