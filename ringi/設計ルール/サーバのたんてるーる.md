## 1. テスト設計方針

### 1.1 使用ツール（UTR-001）

| ツール | 役割 |
|---|---|
| JUnit5 | Java の自動テスティングフレームワーク。Maven 等と連携してビルド時などに自動テストを行う |
| Mockito | JUnit と連携し、自動テスト時にモックを簡単に使えるようにするフレームワーク |
| JaCoCo | JUnit と連携し、自動テストのカバレッジを集計しわかりやすく表示するツール |
| Maven | ビルド構成管理ツール。ビルド時に使用する各種ツールの依存関係や設定、実行タイミングを 1 ファイルで管理 |

### 1.2 テスト単位（UTR-002）

メソッド単位でユニットテストを行う。基本的には手動テストではなくテストコードを作成し、自動テストを行う方針となる。

#### 共通的な考え方

- **UTR-003**: Setter / Getter / toString 等ロジックがないメソッドはテスト対象としない。
- **UTR-004**: 自動生成コードは基本的にテスト対象外とするが、後述の通り Mapstruct 自動生成コードはテスト対象とする。
- **UTR-005**: 直接テストコードから呼び出すのは Public メソッドとし、Protected/Private は Public からの間接的な呼び出しで検証する。それで到達不可能なルートがある場合はまずは処理の見直しを推奨するが、どうしても必要であればリフレクション等で直接起動する。

#### 全レイヤー共通クラス（Constant、Utility など）

- **UTR-006**: ロジックがあるメソッドについてテスト対象とする。

#### プレゼンテーション層

| 対象 | 方針 |
|---|---|
| `<<interface>>Api` | **UTR-007**: バリデーションに対してテストコードを実装（`ApiImpl` 側のテストコードで実装）。Request データモデル・引数は executableValidator の validateParameters で確認。<br>**UTR-008**: Response データモデル・戻り値はテスト対象外（API 仕様書の表現用途でありバリデーションとしては実用しない為） |
| `ApiImpl` | **UTR-009**: テスト対象とする |
| `Model` | **UTR-007**: バリデーションに対してテストコードを実装（`ApiImpl` 側のテストコードで実装）。Request データモデル・引数は executableValidator の validateParameters で確認。<br>**UTR-008**: Response データモデル・戻り値はテスト対象外 |
| `<<interface>>Mapper` | **UTR-009**: Mapstruct 自動生成部分（MapperImpl）についてテスト対象とする。インタフェース部分に default や after 等でロジックがある場合もテスト対象とする |

| 対象 | 方針 |
|---|---|

| `Service` | **UTR-010**: テスト対象とする |
| `ServiceDto`<br>`Repository ⇒ <<interface>>Repository(DB)`<br>`Repository ⇒ <<interface>>Repository(API)`<br>`Entity ⇒ Dto`<br>`Entity ⇒ Table Entity` | **UTR-012**: 上記についてテスト対象外とする（ロジックを書かないルールの為） |

| 対象 | 方針 |
|---|---|
| `RepositoryImpl(DB)` Table 向け | **UTR-014**: MyBatis Generator 自動生成部分についてはテスト対象としない。手動でカスタマイズしている部分についてテスト対象とするが、MyBatisDynamicSql 部分は 4 期 / 5 期では DB モックの使用が難しい為テスト対象としない |
| `RepositoryImpl(DB)` Query 向け | **UTR-015**: テスト対象とするが、4 期 / 5 期では DB モックの使用が難しい為 mockito を使用してモックする |
| `RepositoryImpl(API)` | **UTR-016**: テスト対象とする |
| `Mapper ⇒ <<interface>>Table Mapper` | **UTR-017**: MyBatis Generator による自動生成資源のためテスト対象外とする |
| `Mapper ⇒ <<interface>>Query Mapper` | **UTR-017**: インタフェースのみかつバリデーションも無いためテスト対象外とする |
| `Mapper ⇒ Query Mapper.xml` | **UTR-017**: 4 期 / 5 期では DB モックの使用が難しい為テスト対象としない |

## 2. テストケース設計

### 2.1 テストケース抽出の考え方

テスト対象のメソッドからテストケースを抽出する際の考え方を記載する。

| テスト手法 | カバレッジ | 網羅率 |
|---|---|---|
| ホワイトボックステスト | C1（分岐網羅） | **UTR-018**: 100%（テスト対象メソッドのみ） |

さらにソース上の分岐だけでなく以下についても考慮して抽出する（**UTR-019**）。

- **例外処理**: 発生が期待される例外のテストケースを抽出
- **引数有無**: データ有り・無しのテストケースを抽出
- **アーキ他層 / DB / 外部 API 結果網羅**: インタフェース境界の出力結果を網羅したテストケースを抽出
- **複数回ループ**: ループ 0 回（スキップ）、1 回（開始条件）、複数回（脱出条件）でテストケースを抽出
- **バリデーション**: 発生が期待されるエラーのテストケースを抽出

> **備考**:
> - プロダクトコードからの単純リバースではなくメソッド仕様から抽出すること（作成者など、仕様を知っている人が抽出することが望ましい）。
> - **UTR-020**: 基本的には 1 テストケース ＝ 1 テストコード（メソッド）となる。
> - 成果物はテストコードのみとなるのでテストケース抽出の過程を残すかどうかは任意。
> - **UTR-021**: 分岐で判定させるテストデータは境界値を設定する。

> **備考（C1 分岐網羅について）**:
> それぞれの分岐における真偽が少なくとも 1 回は実行されるようにテストを設計する。例えば以下のような分岐があった場合、
>
> ```java
> if ( a == null && b == null && c == null ){
>    return null
> }
> ```
>
> 以下 2 パターンのテストケースを実行する事で C1 カバレッジとしては網羅される。
>
> - `return null` となる条件（a、b、c すべてが null）
> - `return null` とならない条件（a、b、c いずれかが null ではない）

> **注意**: **UTR-022**: テスト対象メソッドで C1 網羅率 100% がどうしても難しい部分がある場合は個別調整とする。

> **注意**: **UTR-023**: 網羅率 100% の達成したからといって、テストが十分というわけではない。例えば、`if (var ≧ 0)` という条件分岐がある場合、
> - ① `var = 10` と ② `var = -10` の 2 ケースがあれば分岐網羅率は 100% を達成できる。
> - しかし、テストとしては境界値を考慮し ① `var = 0` と ② `var = -1`（③ `var = 1` もあるとなお確実）のケースで検証するべきである。
>
> 網羅率はあくまでテスト完了の必要条件なので、業務仕様としてまたはシステム仕様として検証すべきケースを作成するようにすること。

- テストコードのアサーション等で確認観点を実装する。

## 4. モック方針

### 4.1 テストダブル（モック）の基本方針

以下を Mockito によるテストダブル（モック）に置き換える（**UTR-028**）。

- テスト対象から呼び出される public メソッド（サードパーティ製ライブラリは対象外）
- 単体テスト対象を単体で動作させる上で障壁となる外部依存モジュール

> **注意**: **UTR-029**: protected/private メソッドは基本的には public メソッドと合わせて検証する。protected/private メソッドをモック化する事は JUnit5 では技術的に難しい為、複雑な protected/private の場合期待値を取り出すことが難しくなる。クラス設計の段階で、public から切り出す処理は用途別役割別に別クラス化するなど、極力 protected/private を肥大化しないように処理を見直す事（アーキテクチャとしても protected/private 肥大化は望ましくない）。

> **備考（モック化の必要性）**:
> - 他メソッドに依存しないテストが可能。
> - Mockito 機能により、呼び出しメソッドへ渡す引数の妥当性やメソッド実行回数/順序などのテスト観点を自動的に確認可能。

### 4.2 DB モックについて（UTR-030）

インフラストラクチャ層の DB アクセス部分について、4 期 / 5 期は DB モック（DatabaseRider）ではなく mockito による通常モックで対応できる範囲を試験する。

> **備考**: DB モック：実際の DB を用いて DB アクセス部分をモック化（テストデータ投入、結果検証、事後のデータ戻し）できるツール。

> **備考（世代別例外）**: 6 期相当以降のプロジェクトでは、H2 in-memory + DBRider による単体テストを採用してもよい。単体テストで SQL の実挙動を検証できるという利点があり、4 期 / 5 期当時の DB モック導入困難の状況とは前提が異なるためである。
>
> - **採用判定**: `pom.xml` に `com.github.database-rider:rider-junit5` 依存があり、`src/test/resources/dbrider.yml` および `datasets/*.yml` が配置されていること。
> - **採用例**: `rinsasho-cnt-info-regist-correct-value` の `RinsashoKeisuHoseichiRepositoryImplTest`。
> - **読み分け**: 本節本文（mockito 通常モックの範囲のみ）は 4 期 / 5 期ベースの方針として保持する。世代別の差分は本備考の通り。

### 5.1 ディレクトリ構成（UTR-031, UTR-032）

テストクラスはテスト対象クラスの namespace に準拠して同階層に作成する。また、テストで必要となる共通クラスやリソースがある場合の配置先についても示す。

```
src
├─main
│  ├─java/jp/mufg/bk/yus/presentation/api/impl/sample
│  │  SampleApiImpl.java // テスト対象クラス
│  ├─resource
│  │  // プロダクトで必要なリソースを配置
│  ：
│
└─test
   ├─java/jp/mufg/bk/yus/presentation/api/impl/sample
   │  SampleApiImplTest.java // テストクラス
   ├─java/jp/mufg/bk/yus/test // テストで必要な共通クラスを配置
   │  ├─entity
   │  │   └─SampleEntity.java
   │  └─util
   │     └─SampleUtil.java
   ├─resource
   │  // テストで必要なリソースを配置
   ：
```

> **注意**: CSV ファイルからテストデータを読み込む場合などで、生成ツールを使用して読み込みファイルを生成している場合、その生成ツールも併せて配置する。生成ツールおよび生成されたファイルはテスト範囲に紐づくファイル名にすること（例えばメソッド全体をカバーするならメソッド名を付加するなど）。また、テストクラスもしくは生成されたファイルに、ツールから生成していることが分かるようにコメントを残しておくこと。

**Excel の CSV 生成ツールから生成した CSV ファイルをテストクラスの `getSample` メソッドで読み込む場合の例**:

```
└─test
   └─java/jp/mufg/bk/yus/presentation/api/impl/sample
      SampleApiImplTest.java // テストクラス
       ├─csv
       │  └─SampleApiImplTestData_getSample.csv // CSVファイル
       └─excel
          └─SampleApiImplTestData_getSample.xlsx // CSV生成ツール
```

### 5.9 equals 未実装クラスの比較（UTR-040, UTR-041）

> **注意**: `equals` メソッドが実装されていないクラスに対する `Assertions.assertEquals` や `InOrder.verify`、`Mockito.when` を用いた比較について。

これらは全て与えられた期待値と実測値を比較する動作を行うが、クラス同士の比較にはそのクラス内に実装されている `equals` メソッドを用いる。従って、`equals` メソッドが実装されていなければ Object クラスの `equals` メソッドで比較する事となり、インスタンスアドレス同士の比較となるためどれだけ中身の値が同じでも不一致となる可能性が高い。

#### 戻り値比較の場合（主に `Assertions.assertEquals`） — UTR-040

戻り値比較はユニットテストにおける確認観点の本丸であり、数も基本的には一つのみであることから、`equals` メソッドが実装されていないクラスに対する比較の場合は可能な限り中身のデータを個々に取り出して比較する方針とする。

#### 呼び出し先引数の比較の場合（主に `InOrder.verify`、`Mockito.when`） — UTR-041

本来解であれば呼び出し先引数比較も戻り値比較と同様に中身のデータを個々に取り出して比較すべきであるが、メソッド呼び出しの回数と引数の数によっては膨大な量を比較する必要が出てくる可能性があるため、`equals` メソッドが実装されていないクラスの引数に関しては `any(型)` 比較によるチェックで OK とする。

      final LinkedHashMap<ArgForValidation, HashMap<String, HashMap<Class<? extends Annotation>, String>>> argsAndExpectedViolations,
      final int expectedViolationSize) {

    // ***********************
    // Arrange: テストの準備
    // ***********************

    // violation に渡す可変引数を作成する。合わせてアサーションで使用する、引数インデックス毎の期待するバリデーション情報を作成
    final List<Class<?>> parameterClassList = new ArrayList<Class<?>>();
    final List<Object> parameterValueList = new ArrayList<Object>();
    final List<HashMap<String, HashMap<Class<? extends Annotation>, String>>> expectedViolationsByArgIndex =
        new ArrayList<HashMap<String, HashMap<Class<? extends Annotation>, String>>>();

    for (final Map.Entry<ArgForValidation, HashMap<String, HashMap<Class<? extends Annotation>, String>>> argAndExpectedViolations : argsAndExpectedViolations
        .entrySet()) {
      parameterClassList.add(argAndExpectedViolations.getKey().getArgClass());
      parameterValueList.add(argAndExpectedViolations.getKey().getArgData());

      expectedViolationsByArgIndex.add(argAndExpectedViolations.getValue());
    }

    try {
      final Method method =
          SampleApiImpl.class.getMethod("getSample", // ★ テスト対象のメソッド名
              (Class[]) parameterClassList.toArray(new Class[] {}));
      final Object[] pamameterValues = parameterValueList.toArray();

      // ***********************
      // Act: テスト対象メソッドのバリデーションを実行
      // ***********************
      final Set<ConstraintViolation<SampleApiImpl>> violations = // ★ テスト対象のメソッドを持つクラス
          this.executableValidator.validateParameters(
              this.sampleApiImpl, // ★ テスト対象のメソッドを持つインスタンス
              method,
              pamameterValues);

      // ***********************
      // Assert: 結果の検証
      // ***********************
      Assertions.assertEquals(expectedViolationSize, violations.size());

      // violations が 1 以上の場合、期待するバリデーション検知群と実際のバリデーション検知群が一致するかどうかチェックする
      int matchExpectedViolationsCount = 0;
      for (final ConstraintViolation<SampleApiImpl> violation : violations) { // ★

            violation.getPropertyPath().toString().split("\\.", 2)[1];

            expectedViolationsByArgIndex.get(argIndex).get(argPath);

            violation.getConstraintDescriptor().getAnnotation().annotationType();

          // 期待したバリデーションが発生している場合はメッセージが一致しているかを確認

            matchExpectedViolationsCount++; // 一致した場合は一致カウントをアップ

            Assertions.fail("引数" + violation.getPropertyPath().toString() + "にてバリデーション("
                + constraintType.getName() + ")で期待しないメッセージ発生( expected: "
                + expectedViolations.get(constraintType) + " but was: " + violation.getMessage()
                + " )");
          }
        } else {
          Assertions
              .fail("引数" + violation.getPropertyPath().toString()
                  + "にて期待していないバリデーションのエラー発生( expected: "
                  + expectedViolations.toString() + " but was: " + constraintType.getName() + " )");
        }
      }

      // 期待したバリデーションがすべて発生しているかチェック
      Assertions.assertEquals(expectedViolationSize, matchExpectedViolationsCount);

    } catch (final Exception e) {
      final StringWriter sw = new StringWriter();
      final PrintWriter pw = new PrintWriter(sw);
      e.printStackTrace(pw);
      pw.flush();

      Assertions.fail("exception: " + e.getClass().getName()
          + "  stacktrace: " + sw.toString());
    }
  }

  // 形式：

  //                                                                       バリデーションNGメッセージ>
  //                                      >
  //                 >
  //   , 期待するバリデーションNG数)

        // getSampleメソッド_正常系_userId のバリデーションチェック OK_2C
        Arguments.arguments(

              }
            }, 0),

        Arguments.arguments(

### 6.5 protected/private メソッド（UTR-047）

基本的には public メソッドを経由して試験を行う。それで到達不可能なルートがある場合はまずは処理の見直しを推奨する。ただし、どうしても必要であればリフレクションで protected/private を直接起動する事も可能。

> **注記**: 参考サンプルソースパス：`src/test/java/jp/mufg/bk/yus/presentation/api/impl/zkv0101_productlist/validator/ZkV0101SearchValidatorTest.java`

> **注意**: protected/private メソッドをモック化する事は JUnit5 では技術的に難しい為、複雑な protected/private の場合期待値を取り出すことが難しくなる。クラス設計の段階で、public から切り出す処理は用途別役割別に別クラス化するなど、極力 protected/private を肥大化しないように処理を見直す事（アーキテクチャとしても protected/private 肥大化は望ましくない）。

**テスト対象メソッド**:

```java
@NoArgsConstructor
@RequestValidator
public class SampleSearchValidator {

  public void validate(SampleSearchRequest request) {

    // 検索条件が 1 つもない場合
    if (!containsNonNull(request.getKeyword(), request.getMinPrice(), request.getMaxPrice(),
        request.getGenre(), request.isIsBookmarked(), request.isIsFreeShipping())) {
      // 業務エラーをスロー
      throw new ApplicationBusinessException(MessagesConst.YUSZK0001E, null, ErrorLevel.Error,
          null);
    }

    if (Objects.isNull(request.getMinPrice()) || Objects.isNull(request.getMaxPrice())) {
      return;
    }

    // 価格の下限と上限が逆転している場合
    if (request.getMinPrice() > request.getMaxPrice()) {
      // 業務エラーをスロー
      throw new ApplicationBusinessException(MessagesConst.YUSZK0002E, null, ErrorLevel.Error,
          null);
    }
  }

  /**
   * 引数の配列要素に Null でないものがあれば true、すべての Null なら false
   */
  private boolean containsNonNull(Object... elements) {
    for (Object element : elements) {
      if (Objects.nonNull(element)) {
        return true;
      }
    }
    return false;
  }
}
```

**テストコード（public 経由・間接検証）**:

```java
