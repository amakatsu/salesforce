## 1. プレコーディングでやること

### 1.1 目的（PRC-001）

プレコーディングでは、本格的な製造に入る前に、代表的な機能を 1 つ実装する。

目的は、完成度の高い機能を作ることではなく、実際に手を動かして、製造時に必要となる作業の全体像をつかむことである。

> **ヒント**: プレコーディングは、1 機能を完成させることではなく、製造時に必要な作業量・実装方式・テスト方式を把握するために実施する。

### 1.2 主な確認項目（PRC-002）

主に以下を確認する。

- 実装時に必要となるクラス群
- パッケージ構成やレイヤー構成などのアーキテクチャ
- 自動生成ソースと手実装箇所の境界
- JUnit / Jest のテスト作成量とテストケース観点
- 共通部品や外部依存のモック化方法
- 実装・テスト時に詰まりやすい箇所
- 生産計画・品質計画に反映できる作業量

### 1.3 対象選定（PRC-003）

プレコーディングは、すべての機能を対象にするものではない。軽めの代表機能を 1 つ選び、実装からテストまでの流れを確認する。

## 2. 実施判断と完了の目安

### 2.1 実施判断（PRC-004）

プレコーディングは、必須作業ではない。

直近で実施できない場合は、無理に着手しなくて問題ない。その場合は、以下をもとに生産計画・品質計画へ反映する。

- プレプレコーディング成果物
- 既存の実装例
- 第 4 期の生産性実績
- 各担当者の経験値

### 2.2 翌月以降の再確認（PRC-005）

> **ヒント**: 直近で実施できない場合でも、完全に取りやめるのではなく、来月以降に再度実施可否を確認する。

### 2.3 完了の目安（PRC-006）

実施する場合は、以下が分かればプレコーディングとしては完了である。

- 実装時に必要となるクラス群
- パッケージ構成やレイヤー構成
- 自動生成と手実装の境界
- クライアント側・サーバー側のテスト作成量
- テストケースの主な観点
- モック化が必要な箇所
- 実装・テスト・モック化の物量感
- ホスト連携や相関チェックなど、今後確認すべき残課題

この状態になれば、生産計画や品質計画に反映するための材料として利用できる。

## 3. まず確認する参考実装

### 3.1 参考実装の前提（PRC-007）

プレコーディングの前段として、プレプレコーディングを実施済みである。

- [プレプレコーディング](https://gitlab.rp.common.svc.bkuru0.itmufg/bkyus0/apl/systems/server/production/ringi-kakuzuke/-/me…)
- 併せてテーブル定義・OpenAPI から [自動生成されるコードも作成済](https://gitlab.rp.common.svc.bkuru0.itmufg/bkyus0/apl/systems/server/production/ringi-kakuzuke/-/me…)

| 項目 | 内容 |
| ---- | ---- |
| 対象機能 | 計数情報の補正値登録 |
| 機能種別 | 単純登録 |
| 処理内容 | DB に値を保存する |
| 実装範囲 | クライアント側、サーバー側 |
| 位置づけ | プレコーディング時の参考実装 |

まずは、この参考実装を確認すること。

### 3.2 参考実装で見るポイント（PRC-008）

見るポイントは以下である。

- 画面から API を呼び出す流れ
- サーバー側で登録処理を行う流れ
- DB に保存する流れ
- どのクラスが作成されているか
- どのパッケージに配置されているか
- どこまで自動生成されているか
- どこから手実装しているか
- テストがどの粒度で書かれているか

## 4. アーキテクチャを理解する

### 4.1 アーキテクチャ確認の観点（PRC-009）

参考実装を確認する際は、処理の流れだけでなく、アーキテクチャ上の役割分担も確認する。

特に、どのパッケージにどの責務のクラスが配置されているかを見る。

| 観点 | 確認内容 |
| ---- | ---- |
| パッケージ構成 | クライアント側・サーバー側で、どのようにパッケージが分かれているか |
| レイヤー構成 | 画面、API、Service、Repository、Mapper、DTO などの責務がどう分かれているか |
| 呼び出し方向 | 画面から API、Service、Repository へどの順で処理が流れるか |
| データの受け渡し | Request / Response / DTO / Entity がどこで使われるか |
| 自動生成範囲 | どのパッケージ・クラスが自動生成されるか |
| 手実装範囲 | どのパッケージ・クラスに個別実装を追加するか |

> **ヒント**: 単に「処理が動くこと」ではなく、各クラスの責務、配置場所、データの受け渡し、自動生成と手実装の接続を確認すること。

### 4.2 アーキテクチャ理解時の意識（PRC-010）

参考実装では、画面から登録 API を呼び出し、サーバー側で登録処理を行い、DB に保存するまでの流れを追う。

その際、以下を意識する。

- 各クラスがどのレイヤーに属しているか
- 各クラスの責務がどこまでか
- レイヤー間でどのデータ型を受け渡しているか
- 自動生成されたクラスと手実装クラスがどう接続されているか
- 同じ作り方を他機能にも横展開できるか

プレコーディングでは、このアーキテクチャ理解も含めて、今後の製造で迷わず実装できる状態を目指す。

## 5. 作業の進め方

### 5.1 作業フロー（PRC-011）

作業は、以下の流れで進める。

1. 参考実装を確認する
2. パッケージ構成・レイヤー構成を確認する
3. 対象にする軽めの機能を決める
4. 自動生成されるソースを確認する
5. 手実装が必要な箇所を実装する
6. クライアント側・サーバー側のテストを作成する
7. 必要に応じて共通部品や外部依存をモック化する
8. テスト結果とカバレッジを確認する
9. 実装・テストの物量感を確認する

### 5.2 対象機能の選び方（PRC-012）

> **ヒント**: 対象機能は、難しいものを選ぶ必要はない。実装からテストまで一通り確認できる、軽めの機能を選ぶことを優先する。

## 6. 実装で確認すること

### 6.1 実装時の確認観点（PRC-013）

実装時は、対象機能を作るために必要なクラス構成と、自動生成・手実装の境界を確認する。

| 観点 | 確認内容 |
| ---- | ---- |
| クラス構成 | 対象機能でどのクラスが必要か |
| 配置場所 | どのパッケージにクラスを配置するか |
| 自動生成 | どこまで自動生成されるか |
| 手実装 | どこから個別実装が必要か |
| 生成後の扱い | 再生成時に上書きされる箇所はどこか |
| 実装量 | 実装にどの程度の作業量がかかるか |

### 6.2 作成対象になり得るクラス（PRC-014）

作成対象になり得るものは以下である（一部自動生成）。

- 画面コンポーネント
- API 呼び出し処理
- Controller
- Service
- Repository
- Request / Response
- DTO
- Entity
- Mapper
- Validator

### 6.3 整理度の目安（PRC-015）

> **ヒント**: この時点では、すべてを厳密に整理しきる必要はない。まずは、参考実装と自分の対象機能を見比べて、どのクラスが必要になるかを把握する。

## 7. テストで確認すること

### 7.1 テスト方針（PRC-016）

テストの詳細な作成方針は、既存のクライアントサイド / サーバーサイド開発ガイドに従う。

プレコーディングでは、テスト標準を再定義するのではなく、**1 機能を作るときに、どのようなテストが必要になり、どの程度の物量になりそうか** を確認する。

> **ヒント**: ここではテスト標準の詳細を再掲しない。詳細なカバレッジ基準、モック化ルール、再鑑観点は既存ガイド（[サーバのたんてるーる.md](サーバのたんてるーる.md) 等）を参照すること。

### 7.2 テストの全体像（PRC-017）

| 対象 | 主なテスト内容 | 確認したい物量 |
| ---- | ---- | ---- |
| クライアント側 | 画面表示、入力チェック、ボタン押下、API 呼び出し、エラー表示 | Jest のテストケース数、API や共通部品のモック量 |
| サーバー側 | API 受付、入力チェック、業務ロジック、DB / API 呼び出し、例外処理 | JUnit のテストケース数、Repository や外部 API のモック量 |
| 共通 | 正常系、異常系、分岐、境界値、カバレッジ確保 | 追加テストがどの程度必要か |

### 7.3 クライアント側で見るテスト（PRC-018）

クライアント側では、Jest を使い、LWC の画面・メソッド・UI 要素を確認する。

| テスト対象 | 例 |
| ---- | ---- |
| 初期表示 | 画面表示時に必要な項目が表示されるか |
| 入力チェック | 必須、桁数、形式などが画面項目定義どおりか |
| ボタン押下 | 登録、戻る、キャンセルなどの操作で期待する処理が呼ばれるか |
| API 呼び出し | 入力値をもとに正しいリクエストを送っているか |
| 正常終了 | 登録成功時にメッセージ表示や画面更新が行われるか |
| エラー表示 | API エラーや入力エラー時に想定どおり表示されるか |
| モック化 | Apex メソッド、ワイヤーアダプター、共通コンポーネントなどを置き換えられるか |

### 7.4 サーバー側で見るテスト（PRC-019）

サーバー側では、JUnit5 / Mockito を使い、メソッド単位で確認する。

| テスト対象 | 例 |
| ---- | ---- |
| API 受付 | リクエストを受け取り、Service に正しく渡しているか |
| 入力チェック | 必須、桁数、形式、値の範囲などがチェックされるか |
| 業務ロジック | 条件分岐や計算、編集処理が仕様どおりか |
| DB 呼び出し | Repository に正しい引数を渡しているか |
| 外部 API 呼び出し | 外部連携先へのリクエストや戻り値の扱いが正しいか |
| 戻り値 | Response / DTO が期待どおり作られているか |
| 例外処理 | Repository や外部 API でエラーが起きた場合の処理が正しいか |
| モック化 | Repository、Mapper、外部 API、共通部品などを置き換えられるか |

### 7.5 テストケースの出し方（PRC-020）

テストケースは、プロダクトコードを単純に逆算して作るのではなく、仕様をもとに抽出する。

最低限、以下の観点でケース数を確認する。

| 観点 | 例 |
| ---- | ---- |
| 正常系 | 想定どおり登録できる |
| 入力値の有無 | 値あり／値なし |
| 境界値 | 最小値、最大値、桁数上限、桁数超過 |
| 分岐 | 条件により処理が変わる箇所 |
| 例外系 | DB エラー、外部 API エラー、想定外エラー |
| 外部依存の戻り値 | 正常、0 件、エラー、想定外レスポンス |
| ループ | 0 件、1 件、複数件 |

### 7.6 やらなくてよいこと（PRC-021）

プレコーディングでは、以下は必須ではない。

- テスト標準そのものを見直すこと
- すべての機能のテストケースを作ること
- テストケース一覧などの詳細な中間成果物を作ること
- ReportPortal や CI 設定の詳細確認
- 既存ガイドに記載済みの細かいルールを資料内に再掲すること
- 対象機能に含まれないホスト連携や相関チェックを無理に確認すること

### 7.7 ホスト連携・相関チェックの扱い（PRC-022）

> **注意**: 対象機能にホスト連携や相関チェックが含まれる場合は、実装・テスト・モック化の物量感だけ確認する。

## 8. 必須ではないこと

### 8.1 必須ではない対象（PRC-023）

- ホスト連携や相関チェックのバリデーション／バリデータ

など対象機能に含まれない場合は、無理に確認しなくてよい。

### 8.2 対象に含まれる場合の確認（PRC-024）

> **注意**: 対象機能に含まれる場合のみ、実装方針・テスト方法・モック化方法を確認する。

### 8.3 未確認事項の扱い（PRC-025）

未確認のまま残る場合は、今後の確認事項として扱う。
