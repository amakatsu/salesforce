# コーディング規約

> **本ドキュメントの位置付け**: ringi 配下の各機能で共通に従うコーディング規約。コメント方針、Javadoc 規約、ロガー出力との使い分けを規定する。
> **隣接ドキュメント**: 設計パターン全般は [設計ルール.md](設計ルール.md)、命名規約は [命名規約.md](命名規約.md) を参照。

## 基本姿勢

t-wada 流のリーダブルコードを徹底する。コードは未来の読者に「なぜそう書いたか」を語るためのもの。コメントは **「なぜ」のみ** を書く。

| 原則 | 内容 |
|---|---|
| WHAT はコードが語る | 何をしているかは関数名・変数名・型シグネチャで表現する。コメントで補わない |
| WHY はコメントが語る | なぜその実装を選んだか、なぜその制約があるかを書く |
| 自明なことは書かない | コードを読めば分かることはコメントで重複させない |

## 書いてよいコメント

| 種別 | 例 | 理由 |
|---|---|---|
| 自明でない設計判断 | `// 楽観ロックでは取りこぼす更新があるため、悲観ロック (FOR UPDATE WAIT 30) を併用` | 選択の根拠が将来の読者に伝わらないため |
| 隠れた制約 | `// このメソッドはトランザクション境界の内側でのみ呼ばれる前提` | 呼び出しコンテキストの制約はシグネチャに現れないため |
| 業務上の例外的扱い | `// 補正値が空でも更新を許可（業務上「補正なし」を意味する）` | 業務知識がないと不可解に見えるため |
| Javadoc | （後述） | 公開 API の契約を明示するため |

## 書いてはいけないコメント

| 種別 | 例（NG） | 理由 |
|---|---|---|
| 出典・参照 | `// 出典: ringi/設計ルール/設計ルール.md` / `// memo.text:L80-118` | コードと文書は別管理。文書側が変わるとコメントが嘘になる |
| 変更履歴 | `// 2026/05/07 追加（issue-123）` | git history が正典。コメントは陳腐化する |
| WHAT 説明 | `// i に 1 を足す` / `// 取引先番号を取得する` | コードを翻訳しただけで情報量ゼロ |
| リファクタ前への言及 | `// 旧実装では Hashtable を使っていた` | 旧実装は git history で見れば足りる |
| マーカー | `// ↓↓↓ ここから重要 ↓↓↓` / `// TODO: あとで直す` | 意図不明・腐敗のもと。`TODO` を残すなら issue 番号必須 |
| 無意味な区切り | `//================` | 視覚ノイズ。論理構造はメソッド分割で表現する |

## Javadoc の扱い

### 必須対象

- **全 public class / public method**: 責務を Javadoc で明示する
- **複雑な package-private / protected**: 呼び出し条件が自明でない場合

### 必須要素

| タグ | 用途 |
|---|---|
| 説明文 | クラス／メソッドの **責務** を 1〜3 行で記述 |
| `@param` | 各引数の意味と制約（null 許容性、範囲等） |
| `@return` | 戻り値の意味（`Optional` の空の意味、空リストの意味等） |
| `@throws` | 投げる例外の発生条件（チェック例外は必須、非チェック例外は重要なものだけ） |

### 禁則

- **出典記載禁止**: Javadoc 本文に「設計書 §3.4 参照」「memo.text:L〇〇〇」等を書かない
- **WHAT の繰り返し禁止**: メソッド名で分かることを Javadoc で重複させない
- **`@author` / `@since` / `@version` 不要**: git history で十分

### 例

```java
// OK
/**
 * 計数情報の補正値を主キーで更新する。削除済みレコードは対象外。
 *
 * @param entity 更新対象の補正値。null 不可。複合主キー (店番・取引先番号) は必須
 * @return 更新件数。0 件なら新規登録すべき
 * @throws DataAccessException SQL 実行失敗時
 */
int updateByPrimaryKeyAndDelFlg(KeisuHoseichi entity);

// NG（出典記載・WHAT 説明）
/**
 * 計数情報を更新する。
 * 出典: 設計書 §1.2 Step 5
 * 詳細は memo.text:L80-118 参照。
 *
 * @param entity entity
 * @return int
 */
```

## ロガー出力との使い分け

| 情報の性質 | 手段 | 理由 |
|---|---|---|
| 静的（実装時に確定する） | コメント / Javadoc | 実行時に変わらない。ソースに残す |
| 動的（実行時に決まる） | ロガー | 引数値・処理結果・例外スタック等は実行ログで確認 |
| 業務イベント（監査・運用観点） | ロガー（`info` 以上） | 後追い調査の根拠になる |
| 開発時のデバッグ補助 | ロガー（`debug` / `trace`） | 本番では出力されない |

**禁則**: `System.out.println` の使用、commit に残す `// debug` コメントの放置。

## 命名・冗長性に関する補則

| 観点 | ルール |
|---|---|
| バージョンアップ耐性 | フレームワーク（JAX-RS / MyBatis）の標準 API・公式パターンを優先する。製品の内部実装に依存するハック禁止 |
| 簡潔さ | 同パターンの 3 回以上のコピペは共通化する。冗長な繰り返しは排除 |
| 例外処理 | 「例外 3 種で同じロールバック処理が重複する」ようなコピペは共通化（try-with-resources / template method 等で集約） |
| Optional の扱い | `Optional<T>` の戻り値は `null` を返さない。引数には `Optional` を取らない（呼び出し側に判断を委ねる） |
| `final` の付与 | 引数・ローカル変数・フィールドに `final` を付ける。再代入が必要な箇所だけ外す |
| 引数防衛 | public 境界で `Objects.requireNonNull` 等の null チェックを行う |
