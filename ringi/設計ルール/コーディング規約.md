# コーディング規約

> **本ドキュメントの位置付け**: ringi 配下の各機能で共通に従うコーディング規約。コメント方針、Javadoc 規約、ロガー出力との使い分けを規定する。
> **隣接ドキュメント**: 設計パターン全般は [設計ルール.md](設計ルール.md)、命名規約は [命名規約.md](命名規約.md) を参照。

## 基本姿勢

t-wada 流のリーダブルコードを徹底する。コードは未来の読者に「なぜそう書いたか」を語るためのもの。コメントは **「なぜ」のみ** を書く。

| 原則 | 内容 |
|---|---|
| WHAT はコードが語る | 何をしているかは関数名・変数名・型シグネチャで表現する。コメントで補わない |
| WHY はコメントが語る | なぜその実装を選んだか、なぜその制約があるかを書く |
| 自明なことは書かない | コードを読めば分かることはコメントで重複させない |

## 書いてよいコメント

| 種別 | 例 | 理由 |
|---|---|---|
| 自明でない設計判断 | `// 楽観ロックでは取りこぼす更新があるため、悲観ロック (FOR UPDATE WAIT 30) を併用` | 選択の根拠が将来の読者に伝わらないため |
| 隠れた制約 | `// このメソッドはトランザクション境界の内側でのみ呼ばれる前提` | 呼び出しコンテキストの制約はシグネチャに現れないため |
| 業務上の例外的扱い | `// 補正値が空でも更新を許可（業務上「補正なし」を意味する）` | 業務知識がないと不可解に見えるため |
| Javadoc | （後述） | 公開 API の契約を明示するため |

## 書いてはいけないコメント

| 種別 | 例（NG） | 理由 |
|---|---|---|
| 出典・参照 | `// 出典: ringi/設計ルール/設計ルール.md` / `// memo.text:L80-118` | コードと文書は別管理。文書側が変わるとコメントが嘘になる |
| 変更履歴 | `// 2026/05/07 追加（issue-123）` | git history が正典。コメントは陳腐化する |
| WHAT 説明 | `// i に 1 を足す` / `// 取引先番号を取得する` | コードを翻訳しただけで情報量ゼロ |
| リファクタ前への言及 | `// 旧実装では Hashtable を使っていた` | 旧実装は git history で見れば足りる |
| マーカー | `// ↓↓↓ ここから重要 ↓↓↓` / `// TODO: あとで直す` | 意図不明・腐敗のもと。`TODO` を残すなら issue 番号必須 |
| 無意味な区切り | `//================` | 視覚ノイズ。論理構造はメソッド分割で表現する |

## Javadoc の扱い

### 必須対象

- **全 public class / public method**: 責務を Javadoc で明示する
- **複雑な package-private / protected**: 呼び出し条件が自明でない場合

### 必須要素

| タグ | 用途 |
|---|---|
| 説明文 | クラス／メソッドの **責務** を 1〜3 行で記述 |
| `@param` | 各引数の意味と制約（null 許容性、範囲等） |
| `@return` | 戻り値の意味（`Optional` の空の意味、空リストの意味等） |
| `@throws` | 投げる例外の発生条件（チェック例外は必須、非チェック例外は重要なものだけ） |

### 禁則

- **出典記載禁止**: Javadoc 本文に「設計書 §3.4 参照」「memo.text:L〇〇〇」等を書かない
- **WHAT の繰り返し禁止**: メソッド名で分かることを Javadoc で重複させない
- **`@author` / `@since` / `@version` 不要**: git history で十分

### 例

```java
// OK
/**
 * 計数情報の補正値を主キーで更新する。削除済みレコードは対象外。
 *
 * @param entity 更新対象の補正値。null 不可。複合主キー (店番・取引先番号) は必須
 * @return 更新件数。0 件なら新規登録すべき
 * @throws DataAccessException SQL 実行失敗時
 */
int updateByPrimaryKeyAndDelFlg(KeisuHoseichi entity);

// NG（出典記載・WHAT 説明）
/**
 * 計数情報を更新する。
 * 出典: 設計書 §1.2 Step 5
 * 詳細は memo.text:L80-118 参照。
 *
 * @param entity entity
 * @return int
 */
```

## 規約・一般知識を書かない（DRY）

設計ルール／コーディング規約／フレームワーク公式ドキュメントに既載の内容を、個別ファイルのコメント・Javadoc に重複させてはならない（DRY: Don't Repeat Yourself）。

| 種別 | 書いてはいけない理由 |
|---|---|
| 設計ルール記載済 | `SEPARATION 原則`／`楽観ロック方針`／`Dynamic SQL 第1選択` 等は [DBアクセス.md](DBアクセス.md) / [アーキテクチャ.md](アーキテクチャ.md) / [設計ルール.md](設計ルール.md) を真とする。個別ファイルで再記述すると規約改定時に齟齬が生じる |
| 言語・フレームワーク一般知識 | 「`@Inject` はコンストラクタ DI」「`@Mapper` は MyBatis 識別」「`@ApplicationScoped` は CDI bean」等は公式ドキュメント・JavaDoc の責務 |
| 仕様書写経 | 設計書・memo の文章をそのままコメント転写しない。仕様変更時に陳腐化 |
| 経緯（リファクタ前・変更履歴） | git history が正典 |

> **判断基準**: コメントを書く前に「これは ringi/設計ルール/ または公式ドキュメントを読めば分かるか？」を自問する。Yes なら書かない。

## Javadoc 簡潔ルール

Javadoc は **長く書くほど良い** ものではない。**必要十分な契約情報** を優先する。

| 対象 | ルール |
|---|---|
| クラス Javadoc | **責務を 1 行**（長くても 1〜2 行）。複数段落で責務を細切れに説明しない |
| メソッド Javadoc | **契約**（1 行説明 + `@param` / `@return` / `@throws`）に絞る。本文に WHAT 説明・呼出側状況の詳細を書かない |
| `<ol>` / `<ul>` での責務列挙 | **禁止**。列挙したくなったらクラス分割を疑う（SRP 崩壊のサイン） |
| 段落（`<p>`）の多用 | クラスで `<p>` 2 段落以上は責務肥大の警告。設計見直しまたはリーダブル命名で吸収 |
| `@inheritDoc` | interface 側 Javadoc が十分なら、実装クラスは省略（Java の暗黙継承）か `{@inheritDoc}` 1 行 |

### 例（クラス Javadoc）

```java
// OK: クラス 1 行
/** 計数情報補正値テーブルへの単一テーブル CRUD を担う MyBatis Mapper。 */
public interface KeisuHoseichiMapper { ... }

// NG: 段落多用 + 責務列挙 + 設計ルール再記述
/**
 * 計数情報補正値テーブルへの CRUD。
 *
 * <p>本 interface は SQL 実行専用であり、POJO 変換ロジックは持たない（MapStruct の責務）。</p>
 * <p>排他制御は楽観ロック方針に統一されているため、FOR UPDATE 等の DB 行ロックメソッドは一切定義しない。</p>
 * <ol><li>更新</li><li>挿入</li></ol>
 */
```

NG 例の問題点: (1) `<ol>` での責務列挙 = メソッド名を読めば分かる WHAT、(2)「SQL 実行専用」「楽観ロック方針」= 設計ルール既記載、(3) 段落 2 つ = 規約再記述。

## 残してよいコメント（再掲・優先順）

スリム化判断時の **残す・削る** 早見表。

| ✅ 残す | ❌ 削る |
|---|---|
| クラス 1 行 Javadoc（責務） | 段落 2 つ以上の責務説明 |
| メソッド契約（1 行説明 + `@param` / `@return` / `@throws`） | メソッド本体の WHAT 翻訳 |
| **コード固有 WHY**（なぜこの実装を選んだか、選択肢の中でこの判断に至った理由） | 設計ルール／コーディング規約に既記載の方針 |
| **罠警告**（仮値・非自明な制約・並行性の前提・呼出順序の隠れた依存） | 言語・FW 一般知識 |
| 業務知識が要る例外的扱い | 仕様書文面の写経 |
| `@SuppressWarnings` の理由 | 経緯（リファクタ前・変更履歴・issue 番号のみのコメント） |

## ロガー出力との使い分け

| 情報の性質 | 手段 | 理由 |
|---|---|---|
| 静的（実装時に確定する） | コメント / Javadoc | 実行時に変わらない。ソースに残す |
| 動的（実行時に決まる） | ロガー | 引数値・処理結果・例外スタック等は実行ログで確認 |
| 業務イベント（監査・運用観点） | ロガー（`info` 以上） | 後追い調査の根拠になる |
| 開発時のデバッグ補助 | ロガー（`debug` / `trace`） | 本番では出力されない |

**禁則**: `System.out.println` の使用、commit に残す `// debug` コメントの放置。

## 横断的関心事（AOP / フレームワーク責務）

ロギング・例外処理・トランザクション境界・認証/認可・性能計測等の **横断的関心事** は、業務ロジックと混在させない。**フレームワーク機構** または **専用のアスペクト** に集約し、業務クラス（`ApiImpl` / `Service`）は業務ロジックのみに集中する。

### ログ出力（責務集約）

| 責務 | 担当 | 配置 |
|---|---|---|
| HTTP リクエスト受付・応答ログ | Servlet Filter / JAX-RS `ContainerRequestFilter` / `ContainerResponseFilter` | プロジェクト共通基盤 |
| メソッド実行ログ（業務イベント・開始終了） | CDI Interceptor（`@Logged` 等のメタアノテーション） | プロジェクト共通基盤 |
| 例外発生時のスタックトレース | JAX-RS `ExceptionMapper` / `@ControllerAdvice` 相当 | プロジェクト共通基盤 |
| 監査ログ（業務上の重要操作） | CDI Interceptor + 専用 Logger | プロジェクト共通基盤 |

> **業務クラスでのロガー直接利用禁止**: `ApiImpl` / `Service` 内で `LoggerFactory.getLogger(...)` を直接呼び出さない。`Logger` フィールドの宣言・`LOGGER.info(...)` / `LOGGER.error(...)` 呼出は **禁止**。同等の情報はフレームワーク機構が集約的に出力する。

### 例外処理（責務集約）

| 責務 | 担当 | 配置 |
|---|---|---|
| 業務例外 → HTTP ステータスコード変換 | JAX-RS `ExceptionMapper`（業務例外型ごとに 1 つ） | プロジェクト共通基盤 |
| システム例外 → 共通エラー応答 | 汎用 `ExceptionMapper<Throwable>` | プロジェクト共通基盤 |
| 例外ロギング・スタックトレース出力 | `ExceptionMapper` 内で集約 | プロジェクト共通基盤 |
| トランザクションロールバック | `@Transactional` 宣言（フレームワーク） | `Service` クラスへの宣言のみ |
| HTTP ステータス変換 | `ExceptionMapper` の戻り値（`Response.status(...)`） | プロジェクト共通基盤 |

> **try-catch で囲まない**: `ApiImpl` / `Service` で **再スローのみの try-catch を書かない**。フレームワークが捕捉して集約処理を行う。業務例外（`OptimisticLockException` 等）も握り潰さず透過させる。

#### 例: 違反 vs 推奨

```java
// NG: 再スローのみの try-catch + ロガー直接利用
private static final Logger LOGGER = LoggerFactory.getLogger(...);

public Response foo(Request req) {
    LOGGER.info("受付: {}", req);
    try {
        return service.foo(req);
    } catch (RuntimeException e) {
        LOGGER.error("エラー: {}", req, e);
        throw e;
    }
}

// OK: 業務ロジックのみ
public Response foo(Request req) {
    return service.foo(req);
}
```

NG 側の「受付ログ」「エラーログ」「再スロー」は **すべてフレームワークの責務**。業務クラスから消す。

### 残してよい局所処理

横断的関心事の集約原則と矛盾しない、**個別ロジックに本質的に必要な局所処理** は残す。

| 残してよいもの | 理由 |
|---|---|
| `Objects.requireNonNull` での引数防衛 | メソッド契約（`@param` 制約）の実行時検証。フレームワークでは代替不可 |
| `try-with-resources`（リソース解放） | リソース確実解放はフレームワーク機構の対象外 |
| `finally` ブロック内の **本質的後始末**（ロック解放・状態遷移ロールバック等） | 業務ロジック上の必須後処理。`finally` 内でロギングや再スローは行わない |
| ビジネスルールに基づく `try-catch`（特定例外を **業務的に変換** する場合） | 例外を握り潰すのではなく業務的な意味付けをする場合のみ。Javadoc で意図を明記 |

### 適用範囲

| 層・部品 | 削除対象 | 備考 |
|---|---|---|
| presentation `ApiImpl` | ✅ 対象 | ロガー直接利用禁止・再スローのみの try-catch 禁止 |
| domain `Service` | ✅ 対象 | 同上。`@Transactional` 宣言は責務集約の一部のため保持 |
| infra `RepositoryImpl` / `Mapper` | ❌ 対象外 | データアクセス層独自のセッション管理ログ等は MyBatis 機構に従う |
| 共通ライブラリ（`com.util` 等） | ❌ 対象外 | フレームワーク機構そのもの・横断的関心事の実装側 |
| Servlet Filter / `ExceptionMapper` / CDI Interceptor | ❌ 対象外 | 横断的関心事を **集約する側**。本ルールの規制対象ではなく、責務の引き受け先 |

### 検証手段

PR レビュー時に下記 grep で違反を機械的に検出する。**0 件** であること。

```bash
# presentation/ApiImpl + domain/Service のロガー直接利用と try { 検出
grep -rn 'LoggerFactory\|private.*Logger\|LOGGER\.' \
    src/main/java/.../presentation/api/impl/ \
    src/main/java/.../domain/service/
grep -rn -E '^\s*try\s*\{' \
    src/main/java/.../presentation/api/impl/ \
    src/main/java/.../domain/service/
```

(`try-with-resources` は `try (...) {` のため `try {` 検出には引っかからない)

## 命名・冗長性に関する補則

| 観点 | ルール |
|---|---|
| バージョンアップ耐性 | フレームワーク（JAX-RS / MyBatis）の標準 API・公式パターンを優先する。製品の内部実装に依存するハック禁止 |
| 簡潔さ | 同パターンの 3 回以上のコピペは共通化する。冗長な繰り返しは排除 |
| 例外処理 | 「例外 3 種で同じロールバック処理が重複する」ようなコピペは共通化（try-with-resources / template method 等で集約） |
| Optional の扱い | `Optional<T>` の戻り値は `null` を返さない。引数には `Optional` を取らない（呼び出し側に判断を委ねる） |
| `final` の付与 | 引数・ローカル変数・フィールドに `final` を付ける。再代入が必要な箇所だけ外す |
| 引数防衛 | public 境界で `Objects.requireNonNull` 等の null チェックを行う |

## SQL の記述に関する規約

DB アクセスは **MyBatis Dynamic SQL（Java DSL）** を第 1 選択とする（採用方針は [DBアクセス.md](DBアクセス.md) の「SQL 記述方式」、Mapper 実装パターンは [アーキテクチャ.md](アーキテクチャ.md) の「Mapper 実装規約」を参照）。本節ではコーディング上の禁則を列挙する。

### 禁則

| # | 禁則 | 理由 |
|---|---|---|
| 1 | **SQL リテラル禁止** | `String sql = "SELECT ..."`、StringBuilder 連結、Java text block (`"""SELECT ..."""`) で SQL 文字列を組み立てない |
| 2 | **アノテーション SQL 禁止** | `@Select` / `@Update` / `@Insert` / `@Delete` / `@SelectProvider` 等で文字列 SQL を直書きしない |
| 3 | **Statement 直接利用禁止** | `java.sql.Statement` / `PreparedStatement` の直接利用、および `SqlSession#selectOne(statementId, ...)` 等の動的 statement 名指しは使わない |
| 4 | **Table オブジェクトは別クラス** | `SqlTable` を継承したテーブル定義クラスは Mapper interface 内に書かず、**別ファイル**（`infra/mapper/tables/support/XxxxTable.java`）に切り出す |
| 5 | **`SqlColumn<T>` を public final で公開** | Mapper / RepositoryImpl からは Table support クラスのフィールド経由でカラムを参照する。Mapper 内で `column("xxx", JDBCType.VARCHAR)` を再定義しない |
| 6 | **マジックリテラル禁止** | テーブル名・カラム名は Table support クラスの定数経由で参照する。SQL ビルダの引数に `"xxx"` 文字列を直渡ししない |

### 例: 禁則違反 vs 推奨

```java
// NG: アノテーション SQL（cmd_ringi_014 で禁止）
@Update("UPDATE PERSON SET FIRST_NAME = #{firstName} WHERE ID = #{id}")
int updateFirstName(PersonRecord row);

// NG: 文字列リテラル SQL
String sql = "SELECT * FROM PERSON WHERE ID = ?";
PreparedStatement ps = conn.prepareStatement(sql);

// OK: Dynamic SQL DSL（default method）
default int updateByPrimaryKey(PersonRecord row) {
    return MyBatis3Utils.update(this::update, person, c ->
        c.set(firstName).equalTo(row::getFirstName)
         .where(id, isEqualTo(row::getId)));
}
```

### Table support クラスの実装例

```java
// infra/mapper/tables/support/PersonTable.java
public final class PersonTable extends SqlTable {

    public static final PersonTable person = new PersonTable();

    public final SqlColumn<Long>   id        = column("id",         JDBCType.BIGINT);
    public final SqlColumn<String> firstName = column("first_name", JDBCType.VARCHAR);

    private PersonTable() {
        super("person");
    }
}
```

呼び出し側（Mapper / RepositoryImpl）では `import static ...PersonTable.*;` 等で
カラム定数を取り込み、SQL ビルダに直接渡す。これによりテーブル名・カラム名のリネームが
Java のコンパイラと IDE の参照解析で完全に追跡される。

## テスト戦略

> **適用範囲**: ringi 配下の **全機能横断ルール**。本節の単体テスト方針は補正値登録に限らず、各機能の単体テスト計画にそのまま適用する。

### 単体テストの対象と対象外

殿のご裁可（cmd_ringi_019）に基づき、単体テストは **業務ロジック・データ整合性・変換ロジックを担う層** に集中させる。`Web 層` の通し動作は結合テスト・E2E で検証する方針とする。

| 層・部品 | 単体テスト | フレームワーク | 検証対象 |
|---|---|---|---|
| **domain `Service`** | ✅ **対象** | JUnit 5 + Mockito + AssertJ | ビジネスロジック。Repository / 共通ライブラリ（排他制御ヘルパー等）は Mock |
| **infra `RepositoryImpl`** | ✅ **対象** | JUnit 5 + AssertJ + Database Rider + H2 | Mapper への薄い委譲動作 + 引数防衛 + 例外伝搬。H2 で実 SQL を流す |
| **infra `Mapper`（Dynamic SQL）** | ✅ **対象** | JUnit 5 + AssertJ + Database Rider + H2 | DSL が組み立てる SQL の正確性（カラム指定・WHERE 条件・SET 内容）を H2 への実投入で検証 |
| **presentation/domain Bean Mapper（MapStruct）** | ✅ **対象** | JUnit 5 + AssertJ | フィールドマッピングの完全性。生成された実装クラスを直接呼び出して検証 |
| **presentation `ApiImpl`** | ❌ **対象外** | — | （理由は次節） |

### `presentation/ApiImpl` を単体テスト対象外とする理由

`ApiImpl` は本アーキテクチャでは「**Service への薄いアダプタ**」に役割を限定している（[アーキテクチャ.md](アーキテクチャ.md) presentation 層補足）。具体的には:

| 観点 | 単体テスト対象外とする根拠 |
|---|---|
| ビジネスロジック | 持たない（[アーキテクチャ.md](アーキテクチャ.md) で禁止）→ 単体で検証すべきロジックが存在しない |
| 入力単体チェック | `Model` クラスの **Bean Validation アノテーション** で実施（[設計ルール.md](設計ルール.md) 入力チェック方針）→ 検証は **JAX-RS / Bean Validation フレームワーク責務**。アプリ側で再テストする価値が低い |
| 入力相関チェック | 本機能（および同様の機能）では原則「なし」。発生する場合のみ ApiImpl 内に記述するが、その場合も **結合テスト** で実 HTTP 経路の検証が必須 |
| `Model ↔ ServiceDto` 詰替 | **MapStruct Mapper** が担当（presentation/.../mapper、[アーキテクチャ.md](アーキテクチャ.md)）→ 単体テスト対象は **MapStruct Mapper クラス** であり ApiImpl ではない |
| Service 呼出 | 委譲のみ。Mockito で「Service が呼ばれたか」を検証してもプロダクション価値が低い（過剰な `verify` は禁止、本節「テストで書いてはいけないこと」#5） |
| レスポンス変換 | `Model` への詰替も MapStruct の責務。ApiImpl は受け渡すだけ |

→ ApiImpl 単体テストは **WHAT（薄い委譲）の翻訳** にしかならず、保守コストに見合うリターンが無い。**単体テストを肥大化させない** ため対象外とする。

### Web 層・実 DB の検証は結合テスト / E2E に集約

ApiImpl・JAX-RS バインディング・Bean Validation・実 DB 連携は **結合テスト・E2E**（別計画）で一括検証する。

| 種別 | 検証範囲 | 配置 / 計画 |
|---|---|---|
| 結合テスト（integration） | 単一 API の通し動作（HTTP リクエスト → ApiImpl → Service → RepositoryImpl → 実環境相当 DB） | 別計画文書（本ドキュメント範囲外） |
| E2E（end-to-end） | 認証・他システム連携を含む実環境相当通し動作 | プロジェクト統合テスト計画 |

> **単体テスト肥大化防止の原則**: 単体テストは **業務ロジック・SQL 正確性・変換完全性** の検証に絞る。フレームワークの責務（JAX-RS のルーティング・Bean Validation・MyBatis のセッション管理）を再テストしない。Web 層の通し動作は結合テストへ。

### テスト品質基準

| 項目 | ルール |
|---|---|
| 構造 | **given / when / then** の 3 セクションで構成。コメントまたは空行で区切る |
| メソッド名 | 日本語可。`正常系_対象あり` 形式（アンダースコア区切り）または振る舞いベースの命名 |
| `@DisplayName` | **日本語必須**。テストレポートが自然言語で読める（例: `@DisplayName("対象あり: 更新件数 1 を中継する")`） |
| Assertion | **AssertJ** の `assertThat(...)` を使用。`org.junit.jupiter.api.Assertions.assertEquals` 等は使わない |
| Mock | Mockito の **BDDMockito** スタイル `given(...).willReturn(...)` を推奨（given/when/then と整合） |
| テスト独立性 | テスト間で状態を共有しない。`@BeforeEach` で都度初期化 |
| グルーピング | テスト対象メソッドごとに `@Nested` クラスでグループ化（IDE のテストランナーで階層表示される） |
| テストクラス命名 | `XxxTest`（`src/test/java/...` 配下、本番クラスと同パッケージ） |

### H2 インメモリの限界と影響軽減

H2 は Oracle 完全互換ではないが、本プロジェクトでは下記理由により実質的な影響はほぼない。

| 限界 | 影響軽減策 |
|---|---|
| **Oracle 方言差異**（`SYS_CONTEXT` / `CONNECT BY` / 階層問合せ等のベンダ固有関数は H2 で動かない） | 本プロジェクトは [DBアクセス.md](DBアクセス.md) の通り MyBatis Dynamic SQL の標準 DSL のみを使用する。Dynamic SQL は **ANSI SQL** を生成するので、H2 でほぼ問題なく動作する |
| **悲観ロック挙動の差**（`FOR UPDATE WAIT n` のタイムアウト挙動が H2 と Oracle で異なる） | 本プロジェクトは [DBアクセス.md](DBアクセス.md) の通り **楽観ロックに統一**。悲観ロックは禁止のため、この差異は影響しない |
| **JDBCType 互換**（Oracle 固有型 `NUMBER`(精度) / `CLOB` 等の挙動差） | `SqlTable` で `JDBCType.VARCHAR` / `INTEGER` / `BIGINT` 等の **標準 JDBCType** を使用する限り影響なし |
| **トランザクション分離レベル**（H2 のデフォルト分離レベルは Oracle と異なる場合あり） | テストでは `@DBRider` のトランザクション境界に従う。複数同時トランザクションを伴う検証は infra 単体テストの責務外（結合テストへ） |

> **方針**: H2 で再現できない振る舞い（ベンダ固有の挙動依存・並行性・性能）は、結合テスト（実 DB）または本番相当の検証環境で確認する。infra 単体テストの目的は **「SQL が想定通りカラム・条件で組み立てられて発行される」** ことの検証である。

### テスト責務範囲

| 種別 | 対象 | フレームワーク | 配置 |
|---|---|---|---|
| **単体テスト**（unit） | domain `Service` / infra `RepositoryImpl` / infra `Mapper` / MapStruct Mapper（**presentation `ApiImpl` は対象外**） | JUnit 5 + Mockito + AssertJ（+ Database Rider + H2 for infra） | `src/test/java/.../<対象クラス>Test.java` |
| **結合テスト**（integration） | 単一 API の通し動作（HTTP → presentation → domain → infra）。**ApiImpl・JAX-RS・Bean Validation・実 DB 連携の検証はここで一括実施** | （別途設計、本ドキュメント範囲外） | `src/test/java/.../<対象>IT.java` または別モジュール |
| **E2E テスト**（end-to-end） | 実環境相当（DB ・他システム・認証等を含む）通し動作 | （プロジェクト統合テスト計画に従う、本ドキュメント範囲外） | 別リポジトリまたは `e2e/` |

> **本コーディング規約のスコープ**: 単体テスト（および infra 単体テストとしての H2 利用）。結合テスト・E2E は別文書で規定する。

### infra 単体テストの実装パターン（Database Rider）

- **データセット**: YAML / JSON 形式でテストデータを記述（Database Rider 標準形式）。テストクラスからアノテーションで参照する。
- **主要アノテーション**:
  - `@DBRider`（クラス or メソッドに付与）: Database Rider を有効化
  - `@DataSet("...")`: テスト実行前のデータセット
  - `@ExpectedDataSet("...")`: テスト実行後の期待データセット（差分検証）
- **配置**: テストデータは `src/test/resources/datasets/...` に集約し、テストクラスからの相対参照で揃える。
- **対象メソッド**: 各 Mapper / RepositoryImpl メソッドにつき「正常系 1 件」「対象なし（更新件数 0）」「PK 重複（INSERT 失敗）」などの代表ケースを網羅。

### テストで書いてはいけないこと

| # | 禁止事項 | 理由 |
|---|---|---|
| 1 | `Thread.sleep(...)` での待機 | 不安定（flaky）テストの温床。タイミングは Awaitility 等の専用 API で待つ |
| 2 | 実環境 DB（開発用 Oracle 等）への接続を前提とした **単体テスト** | CI 環境で再現できない。H2 インメモリで完結させる |
| 3 | `if (条件) assertThat(...)` のような条件分岐 assertion | テスト失敗時に何が起きたか分からなくなる。条件ごとに別テストへ分割 |
| 4 | テストメソッド名・DisplayName が `test1` / `testOk` 等の無意味命名 | 失敗ログから状況が読み取れない |
| 5 | `verify(mock, times(N))` での過剰な呼出回数検証 | 実装変更に脆弱。**動作結果**（戻り値・状態）の検証で十分。回数検証は副作用が観測点である場合のみ |
| 6 | 1 テストメソッドで複数の関心事を検証（複数の振る舞いに同時 assert） | 失敗箇所が特定しにくい。**1 テスト 1 振る舞い** |
| 7 | Production コードに依存した固定値（時刻・ランダム値・UUID）をハードコード比較 | 実行ごとにずれる。`Clock` / `RandomGenerator` を注入可能にして固定する |
| 8 | presentation `ApiImpl` の単体テスト | フレームワーク責務を再テストするのみで保守コストに見合わない（前述「ApiImpl を単体テスト対象外とする理由」参照） |
| 9 | フレームワーク（JAX-RS / Bean Validation / MyBatis のセッション管理 等）の挙動再テスト | プロダクション価値ゼロ。フレームワーク自身のテストに任せる |

### t-wada 観点チェックリスト（8 カテゴリ）

和田卓人氏のテスト設計観点を集約したレビューチェックリスト。テスト追加・改修時に **必ず通過** すること。

#### A. 命名・構造

- [ ] テストクラス名は `<対象クラス>Test`（または結合用 `<対象>IT`）になっているか
- [ ] テスト対象メソッドごとに `@Nested` クラスでグループ化されているか
- [ ] `@DisplayName` は **日本語の仕様文**（仕様書・要件として読める文）になっているか（例: 「対象あり (PK 一致 + DEL_FLG=0): 補正値カラムを更新し、件数 1 を返す」）
- [ ] テストメソッド名は振る舞いベース（`PK不一致_件数0かつDB不変` のように **状態と期待結果** が読めるか）
- [ ] `given` / `when` / `then` のセクションがコメントまたは空行で明示されているか

#### B. 網羅性（境界値・同値分割）

- [ ] **境界値**: 0 / 1 / 最大値 / null / 空文字 / 最大桁数 を網羅しているか
- [ ] **同値分割**: 各等価クラスから代表値を選んでいるか（全パターン羅列ではない）
- [ ] **異常系**: 例外送出・件数 0 件・ロールバック条件等が必ず 1 ケース以上あるか
- [ ] パラメタライズで網羅可能な場合は `@ParameterizedTest` + `@CsvSource` / `@MethodSource` を使う（テスト本体重複を避ける）
- [ ] **論理削除**: `DEL_FLG=1` を含むデータでフィルタが効いているか（Repository / Mapper 限定）

#### C. テスト独立性

- [ ] テスト間で状態を共有していない（`@BeforeEach` で初期化、`static` 可変フィールドなし）
- [ ] 実行順序に依存していない（`@Order` 等を使わない、もしくは使う場合は理由を Javadoc に明記）
- [ ] 外部リソース（`System.currentTimeMillis` / 環境変数 / ファイルシステム）に依存しない、または Test Double で固定する

#### D. 可読性

- [ ] 1 テストメソッド = 1 振る舞い（複数の `assertThat` でも論理的に 1 関心事）
- [ ] テスト本体が **20 行以内** に収まっているか（超えるならヘルパ抽出または `@ParameterizedTest` 化）
- [ ] テストデータ生成は `newEntity(...)` / Builder / Fixture ファクトリで意図が明確か（テスト本体に setter を 10 連発しない）
- [ ] AssertJ の流暢な API を使い、何を検証しているかが文として読めるか（`assertThat(actual).hasSize(3).contains("X")`）

#### E. アンチパターン排除

- [ ] **Magic Number / Magic String 禁止**: PK・期待値・カラム値は意図のある変数名 or データセットで表現
- [ ] **assert なしテスト禁止**: `@Test` 内で必ず 1 つ以上の assertion を持つ（`verify` のみは原則 NG、副作用観測時に限定）
- [ ] **過剰な `verify(mock, times(N))` 禁止**: 動作結果（戻り値・状態・データセット）の検証で十分
- [ ] **try/catch で握りつぶして手動 fail() 禁止**: `assertThatThrownBy(...)` を使う
- [ ] **テストの中でテストしない**: `if` / `for` で条件分岐 assertion をしない

#### F. Service 固有（domain）

- [ ] Repository / 共通ライブラリは **Mock 化** しているか
- [ ] ビジネスルールごとに `@Nested` で分割しているか（楽観ロック失敗・更新件数 0 でフォールバック・例外伝搬 等）
- [ ] **トランザクション境界の宣言** がテスト対象に含まれる場合、トランザクション開始・コミット・ロールバックの分岐を最低 1 ケースずつ網羅
- [ ] ServiceDto の入出力が「プレゼンテーション層で妥当性チェック済」前提に立っているか（不正値テストは ApiImpl/Bean Validation 側の責務として持ち込まない）

#### G. Repository 固有（infra）

- [ ] **H2 in-memory + Database Rider** を使っているか（Mock のみで完結させない、SQL の正確性を実投入で検証）
- [ ] `@DataSet` で初期データ投入、`@ExpectedDataSet` で期待データ検証（差分検証）
- [ ] **Mapper への委譲** の他に、**引数防衛**（`Objects.requireNonNull`）と **例外伝搬** を独立ケースで検証
- [ ] **論理削除条件**（`DEL_FLG=0`）でのフィルタ動作を検証ケースに含む
- [ ] **PK 不一致** / **対象なし** の各分岐で「件数 0 + DB 不変」を検証

#### H. Mapper 固有（Dynamic SQL）

- [ ] DSL が組み立てる SQL の **WHERE 条件** が想定通りカラムを使うか（PK 不一致時の件数 0 で間接検証）
- [ ] DSL が組み立てる SQL の **SET 句** が想定通りカラムのみ更新するか（`@ExpectedDataSet` で他カラム不変を検証）
- [ ] **null 値** の更新挙動（`null` を SET して NULL になるか、無視されるか）が要件と整合するか
- [ ] **INSERT 全カラム** がマッピング漏れ無く投入されるか（`@ExpectedDataSet` で全カラム期待値を持つ）
- [ ] **PK 重複** 時に `PersistenceException` が伝搬するか（一意制約違反シナリオ）

> **使い方**: PR レビュー時に本リストを開き、各項目をチェック。1 項目でも未達なら **マージ前に対処**。
> **更新方針**: 本リストは生きたドキュメント。新しいアンチパターンを発見したら追加する（git history で経緯は追える）。
