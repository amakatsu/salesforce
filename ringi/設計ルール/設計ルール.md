# 設計ルール

> **本ドキュメントの位置付け**: ringi 配下の各機能で共通に従う設計ルール。ドメイン層設計パターン、入力チェック方針、自動生成ルール、層間データ受け渡し、リポジトリパターン、コーディング品質ルールを規定する。
> **隣接ドキュメント**: 各層の責務は [アーキテクチャ.md](アーキテクチャ.md)、命名規約は [命名規約.md](命名規約.md)、DB アクセスは [DBアクセス.md](DBアクセス.md) を参照。

## ドメイン層の設計パターン

| パターン | 採用方針 |
| --- | --- |
| トランザクションスクリプトパターン | **本システムの前提**。旧システム更改で既存ロジックの再利用性とコスト/品質面の優位を考慮 |
| ドメインモデルパターン | 適用可能かつ効果が高い個別機能のみ採用 |

### トランザクションスクリプトパターンの特徴

- 状態（業務データ）を保持するクラスと振る舞い（メソッド）を持つクラスを **別々のクラス** として実装する。
- 状態を持つクラスは getter/setter のみが定義された POJO クラス。
- 振る舞いを持つクラスはサービスクラスであり、POJO クラスからデータを取得し計算処理やデータ加工処理を行う。サービスクラスはステートレス。
- いわば「手続き型プログラミング」を踏襲した設計パターン。

| 観点 | 内容 |
| --- | --- |
| メリット | 処理の流れがシンプルで可読性が高い。設計・実装難易度が低くキャッチアップが容易 |
| デメリット | ビジネスロジックがサービスクラスに集中するので肥大化を招く。複数のサービスクラスが似たロジックを保持する傾向 |

### ドメインモデルパターンの特徴

- 1 つのクラスの中に状態と振る舞いを実装する（ドメインオブジェクト）。
- 設計難易度は高いが、業務領域を正しく設計に落とし込めれば改修影響度や保守性において非常に効果的。

### DDD 用語使用に関する注意

- 以降の説明には、Eric Evans の "Domain-Driven Design (2004, Addison-Wesley)" で説明されている用語が登場する。
- ただし、**用語は使用しているが "Domain-Driven Design" の考えに則っているわけではない** ことに注意されたい。

## 入力チェック方針

| チェック種別 | 実施場所 | 実装手段 |
| --- | --- | --- |
| 入力単体チェック | プレゼンテーション層（`ApiImpl`） | `Model` クラスの Bean Validation |
| 入力相関チェック | プレゼンテーション層（`ApiImpl`） | `ApiImpl` クラス内で実施 |
| DB 相関チェック | ドメイン層（`Service`） | DB 上のデータとの整合性 |

## 自動生成ルール

| 生成対象 | 生成ツール | 注意事項 |
| --- | --- | --- |
| `Api` インターフェース | OpenAPI Generator | JAX-RS アノテーション（`@Path` / `@Produces` 等）が `Api` 側に付与される |
| `Model` クラス | OpenAPI Generator | Bean Validation アノテーションも自動生成可 |
| Table Mapper | MyBatis Generator | 単一テーブル CRUD のみ。実装クラスは MyBatis-CDI が動的生成 |
| Query Mapper（XML） | （自動生成不可） | 手動作成または自作ツール生成 |

> **重要**: `ApiImpl` クラスでは **JAX-RS アノテーションを付与してはならない**。`Api` インターフェース側のアノテーションが無効化されるため。

## 層間データ受け渡し

- `Model` ↔ `ServiceDto` の変換処理を愚直に実装するとコードが肥大化するため、**Bean マッピング機能を推奨**。
- `ServiceDto` クラスはドメイン層に配置し、ドメインロジックを持たせない POJO とする。
- プレゼンテーション層で妥当性チェック済のデータが渡るので、`Service` クラス側で再チェック不要。

### Bean Mapper の実装手段

| 観点 | 採用 |
|---|---|
| Bean Mapper | **MapStruct** |
| 生成方式 | コンパイル時アノテーションプロセッサにより実装クラスを生成 |
| 型安全性 | フィールド名・型の対応がコンパイル時に検証される（リフレクション不使用） |
| 連携 | CDI / Spring いずれの DI コンテナにも組み込み可能 |
| 配置 | `presentation/.../mapper`（Model ↔ ServiceDto）、`domain/service/.../mapper`（ServiceDto ↔ Entity） |

#### 禁則

- **`BeanUtils.copyProperties`（Spring / Apache Commons）系の使用禁止**: 実行時リフレクションで型不一致を見逃す、フィールド追加に追従できない、IDE の参照解析でフィールドが「未使用」と誤判定される等、保守性を毀損する。
- **MapStruct でクエリ／DB アクセスを書かない**: MapStruct は POJO 変換専用。SQL は MyBatis Mapper（[DBアクセス.md](DBアクセス.md) 参照）の責務。
- **Mapper の中でビジネスロジックを書かない**: 変換は副作用なしの純粋関数として実装する。

## リポジトリパターン

- **依存性逆転**: `Repository` インターフェースをドメイン層に配置、実装クラスをインフラ層に配置。
- **適用範囲**: 本アーキでは外部連携・DB アクセスの **両方** に Repository パターンを適用。
- **本システムの Repository は DDD の「集約」単位の永続化リポジトリとは別文脈**。
- 外部連携仕様の変更（例: SOAP → HTTP）が発生してもインフラ層のみの改修で済む。

## 楽観ロック実装パターン

排他制御は **楽観ロックに統一** する（悲観ロック禁止の根拠は [DBアクセス.md](DBアクセス.md) の「排他制御（楽観ロック原則）」を参照）。

### 適用箇所

- 状態を更新するすべての `Service` クラス（更新系メソッド）。
- 参照系であっても整合性チェックの一部として排他キー検証が必要な場合は同様。

### 標準フロー（Service クラスでの実装）

| 順 | アクション | 備考 |
|---|---|---|
| 1 | リクエストから `lockInfo.exclusiveKey` と `lockInfo.exclusiveCount` を取り出す | プレゼンテーション層で Bean Validation 通過済の前提 |
| 2 | 共通ライブラリ「排他制御ヘルパー」の「排他チェック」を呼出す | 入力: 排他キー / 排他回数。戻り値: 更新後の排他回数 |
| 3 | 戻り値をサービスアウトプット DTO に設定 | クライアントは次回リクエストで更新後排他回数を送る |
| 4 | 業務更新処理（UPDATE / INSERT 等）を実施 | UPDATE 件数 0 の場合のフォールバック（新規登録）も `Service` で判定 |
| 5 | 排他チェックヘルパーが例外を投げた場合はそのままクライアントへ返却 | 握りつぶし禁止 |

### Mapper / RepositoryImpl の設計制約

- **Repository インターフェース・実装に `lock` / `lockBy...` / `selectForUpdate` 等の DB ロック専用メソッドを定義しない**。
- 「対象行検索 + 排他ロック取得」のような独立ステップを Service に書かない。
- UPDATE 件数 0 件時の INSERT フォールバックは、Service 層で「`updateByPrimaryKey...` の戻り値が 0 なら `insertTo...` を呼ぶ」と表現する（`MERGE` / `UPSERT` の DB 機能には依存しない）。

### 例外的に悲観ロックを採用する場合

- 真にやむを得ない場合のみ、**設計レビュー承認** を経て採用可。
- 採用時は当該機能の `design/09_open_questions.md`（または相当文書）に「本機能は本ルールの例外として悲観ロックを採用する旨」と「採用根拠」「承認者」を明記する。

## コーディング品質ルール（殿の勅令）

memo.text に明文記載は無いが、本プロジェクト共通の品質基準として明記する。

| 原則 | 内容 |
|---|---|
| バージョンアップ耐性 | フレームワーク（JAX-RS / MyBatis）の標準 API・公式パターンを優先する。製品の内部実装に依存するハック禁止 |
| リーダブルコード | t-wada 流。意図が読める変数名・関数名で表現する |
| 簡潔さ | 同パターンの 3 回以上のコピペは共通化する。冗長な繰り返しは排除 |
| コメント方針 | 「**なぜ必要か**」のみ記述。経緯・変更履歴・自明説明（`// 変更済み` 等）は書かない。レガシー Java の Javadoc に見られる `Date / Name / Reason for change` 方式は新方式では採用しない |
| 例外処理 | レガシー Java に見られる「例外 3 種で同じロールバック処理が重複する」パターンを避け、共通化する |
