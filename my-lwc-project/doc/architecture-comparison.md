**アーキテクチャ** | 一枚岩（ゴッドクラス） | レイヤー分離（API/サービス/リポジトリ）

**データフロー** | 画面 → ゴッドクラス → DB | 画面 → API → サービス → リポジトリ → DB
==
**責務: 検証** | ゴッドクラスで実施 | API層で実施（バリデーション・入力変換）
**責務: ビジネスロジック** | ゴッドクラスで実施 | サービス層で実施（手順・Tx境界）
**責務: 永続化** | ゴッドクラスで実施 | リポジトリ層で実施（データ永続化）
==
**差分の注入方法** | Factory経由で注入（画面項目差分/登録差分） | 稟議単位で準備（API/サービス/リポジトリ各層）
**API層の差分** | （なし） | XX稟議 登録APIコントローラ / Request DTO / Mapper
**サービス層の差分** | （なし） | XX稟議 入力DTO / 業務差分サービス
**リポジトリ層の差分** | （なし） | XX稟議 永続化マッパー / DBエンティティ / MyBatisMapper
==
**問題点1** | ❌ 全ロジックが集中 | ✅ 責務が分離されている
**問題点2** | ❌ 変更影響が大きい | ✅ 共通処理が集約されている
**問題点3** | ❌ テストが困難 | ✅ テスタビリティが向上
**問題点4** | ❌ 保守性が低い | ✅ 保守性が向上
**問題点5** | ❌ 差分が稟議単位で分離されていない | ✅ 差分は稟議単位で吸収
==
**新規稟議追加時の作業** | 既存ゴッドクラスに追加 | 稟議単位の差分のみ追加
**新規稟議追加時の影響** | 影響範囲が広い（全体に影響） | 影響範囲が限定的（稟議固有のみ）

## 主な改善ポイント

### 1. レイヤー分離
- **API層**: リクエスト受付、バリデーション、入力変換
- **サービス層**: ビジネスロジック、トランザクション境界
- **リポジトリ層**: データ永続化

### 2. 差分の局所化
- 稟議ごとに必要な差分のみを実装
- 共通処理は共通コンポーネントで実装
- Factory パターンで差分を注入

### 3. 疎結合化
- 共通インターフェース（稟議入力IF）で統一
- 依存性注入による柔軟性向上
- 変更影響の局所化

### 4. 保守性向上
- 単一責任の原則に準拠
- テストコードの記述が容易
- 新規稟議の追加が簡単
