# 画面遷移の責任分離（フロント移管）

## 背景
- 稟議画面が複数ある
- データの選択により遷移先が変わる
- これまで: DBに画面IDを持ち、バックエンドから受け取って遷移
- 方針変更: 画面/バックエンドの責任分離により、遷移ロジックをフロントに移管

## 方針
- バックエンドは「遷移判断に必要な最小データ」だけ返す
- 画面IDや画面名は返さない
- フロントでルーティングを決める

## 実現方法の選択肢（深掘り）

### A. JS関数として実行（共通JSをimport）
- 共通のルーティング関数をコンポーネントとしてデプロイ
- 各画面でimportして判定・遷移を実行
-
**メリット:**
- 画面ごとの判断分岐を最小化できる
- 変更反映が速い（LWCデプロイのみ）
- テストが書きやすい（関数単位）

**デメリット:**
- import/利用箇所が分散すると差分管理が難しい
- 画面ごとに呼び出し忘れが起きると動作差が出る
- ルール追加の影響範囲が読み取りづらい

```javascript
// routeResolver.js
export const resolveRoute = (data) => {
  if (data.type === "A" && data.level >= 3) return "ringi-a-detail";
  if (data.type === "B") return "ringi-b-detail";
  if (data.isSpecial === true) return "ringi-special";
  throw new Error("該当する画面がありません");
};
```

```javascript
import { resolveRoute } from "c/routeResolver";

const routeName = resolveRoute(resultFromApi);
this[NavigationMixin.Navigate]({
  type: "standard__navItemPage",
  attributes: { apiName: routeName }
});
```

### B. クッションページで振り分け
- Salesforce側にクッションページを用意
- 各画面からのURLは固定
- クッションページが判断して遷移

**メリット:**
- 入口が一箇所で運用が簡単
- 画面URLが固定で運用ルールが単純
- 画面追加のときの影響範囲が明確

**デメリット:**
- 余計な画面遷移が1回増える
- クッションが単一障害点になりやすい
- ユーザー体感の遅延が出やすい

```javascript
// cushionPage.js
import { resolveRoute } from "c/routeResolver";

connectedCallback() {
  const routeName = resolveRoute(this.resultFromApi);
  this[NavigationMixin.Navigate]({
    type: "standard__navItemPage",
    attributes: { apiName: routeName }
  });
}
```

### C. ルーティング設定ファイル（JSON/Custom Metadata）
- ルールをコードではなく設定に寄せる
- フロントは設定を読み込んで判定する

**メリット:**
- ルールの変更がデプロイなしで可能
- 運用者が触れる範囲を広げられる
- 画面追加/変更の履歴管理がしやすい

**デメリット:**
- 設定のバリデーションが必要
- 条件表現が複雑になると保守性が下がる
- 誤設定のリスクが高い

**簡潔イメージ:**
```json
// route-config.json
[
  { "when": { "type": "A", "levelMin": 3 }, "route": "ringi-a-detail" },
  { "when": { "type": "B" }, "route": "ringi-b-detail" }
]
```
```javascript
const hit = config.find((r) =>
  r.when.type === data.type && (!r.when.levelMin || data.level >= r.when.levelMin)
);
```

### D. バックエンドが「判定に必要なタグ」だけ返す
- 画面IDではなく、分類タグを返す
- フロントがタグと画面の対応だけ持つ

**メリット:**
- 画面IDの責務はフロントに寄せられる
- バックエンドはロジック最小で済む
- フロント側の可読性が上がる

**デメリット:**
- タグの定義が増えすぎると混乱する
- タグ設計の責務が曖昧になる
- 画面追加のときにタグ設計の議論が必要

**簡潔イメージ:**
```json
// APIレスポンス
{ "screenTag": "RINGI_A_HIGH" }
```
```javascript
const tagToRoute = { RINGI_A_HIGH: "ringi-a-detail" };
const route = tagToRoute[data.screenTag];
```

### E. 入口APIで「遷移先候補リスト」だけ返す
- バックエンドは候補の集合を返す
- フロントが最終決定

**メリット:**
- 判定ロジックを柔軟に分担できる
- 既存のバックエンドロジックを活かせる
- 段階的な移行に向く

**デメリット:**
- フロントとバックエンドの二重判定になりやすい
- 最終判断の責任が不明確になる
- 実装が複雑になりがち

**簡潔イメージ:**
```json
// APIレスポンス
{ "candidates": ["ringi-a-detail", "ringi-b-detail"] }
```
```javascript
const route = candidates.find((r) => r !== "ringi-b-detail") || candidates[0];
```
## 共通の判定テーブル

### 画面定義テーブルをフロントに持つ
```javascript
// routeMap.js
export const screenRouteMap = [
  {
    key: "A",
    match: (data) => data.type === "A" && data.level >= 3,
    route: "ringi-a-detail"
  },
  {
    key: "B",
    match: (data) => data.type === "B",
    route: "ringi-b-detail"
  },
  {
    key: "C",
    match: (data) => data.isSpecial === true,
    route: "ringi-special"
  }
];

export const resolveRoute = (data) => {
  const hit = screenRouteMap.find((rule) => rule.match(data));
  if (!hit) {
    throw new Error("該当する画面がありません");
  }
  return hit.route;
};
```

### バックエンドからは判断材料だけ取得
```javascript
// response例（画面IDは含めない）
{
  "type": "A",
  "level": 3,
  "isSpecial": false
}
```

## 運用ポイント
- 画面追加時は `screenRouteMap` を更新
- 判定条件は「データに依存する条件」だけに限定
- バックエンド側は「判定に必要な項目」を返す責務のみ

## 選定の考え方
- 入口を一本化したい: B
- 画面間の独立性を保ちたい: A
- 運用でルールを触りたい: C
- 役割分担を明確にしたい: D
- 移行中で柔軟性が必要: E

## 判断基準
- 画面IDをDBに持たない
- 画面IDをAPIで返さない
- ルーティングはフロントの責務に固定
